## Section 1 — Platform Overview & Assumptions

**UrbanServe Nigeria** is a unified Service Commerce Operating System serving five service verticals across three Nigerian cities. It operates a franchise model (per-city licensees) with corporate-managed brand standards, centralised payment rails, and AI-native customer and provider experiences.

### Multi-Tenant Hierarchy

```
Platform (UrbanServe Global)
  └── Country: Nigeria
        ├── Region: South-West → City: Lagos
        │     ├── Enterprise: UrbanServe Lagos Ltd
        │     │     ├── Franchise: Victoria Island Branch
        │     │     ├── Franchise: Lekki Branch
        │     │     └── Franchise: Ikeja Branch
        ├── Region: North-Central → City: Abuja
        │     └── Enterprise: UrbanServe Abuja Ltd
        │           ├── Franchise: Maitama Branch
        │           └── Franchise: Wuse II Branch
        └── Region: South-South → City: Port Harcourt
              └── Enterprise: UrbanServe PH Ltd
                    └── Franchise: GRA Branch
```

### Assumptions

- All monetary values stored as integer kobo (₦1 = 100 kobo)
- Booking conflict prevention at DB level via `EXCLUDE USING gist` — never application-level
- Phone OTP is the primary auth method; email is optional
- RLS enabled on every table; service role key is server-only
- Paystack processes all payments; no direct card storage
- WhatsApp Business API (Meta Cloud v19.0) used for post-booking notifications when customer opts in
- Termii used for OTP and SMS fallback
- Staff leaderboard refreshed daily at 00:00 WAT (UTC+1 = 23:00 UTC prior day)
- Coupon codes stored UPPER-CASE; validated in Edge Function before any DB write
- `tenants.config` is the single source of truth for per-tenant rates, payment providers, and feature flags

```sql
-- Waitlist notification trigger: fires when a booking is cancelled or no_show
CREATE OR REPLACE FUNCTION notify_waitlist() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.status IN ('cancelled','no_show') AND OLD.status NOT IN ('cancelled','no_show') THEN
    INSERT INTO automation_jobs (tenant_id, job_type, payload, run_at)
    SELECT NEW.tenant_id, 'notify_waitlist',
           jsonb_build_object('service_id', NEW.service_id, 'slot_date', NEW.starts_at::date),
           now()
    WHERE EXISTS (
      SELECT 1 FROM waitlist_entries
      WHERE service_id = NEW.service_id AND status = 'waiting'
        AND preferred_date = NEW.starts_at::date);
  END IF;
  RETURN NEW;
END;$$;
CREATE TRIGGER trg_notify_waitlist
  AFTER UPDATE ON bookings FOR EACH ROW EXECUTE FUNCTION notify_waitlist();
```

```sql
-- Staff leaderboard (refreshed daily at 23:00 UTC by pg_cron)
CREATE MATERIALIZED VIEW staff_leaderboard AS
SELECT
  sm.id           AS staff_id,
  sm.tenant_id,
  sm.profile_id,
  p.full_name,
  COUNT(b.id)     AS completed_bookings,
  COALESCE(SUM(b.total_amount_kobo), 0)  AS revenue_kobo,
  COALESCE(SUM(g.amount_kobo), 0)        AS tips_kobo,
  COALESCE(AVG(r.rating), 0)::numeric(3,2) AS avg_rating,
  COUNT(DISTINCT r.customer_id)           AS review_count,
  RANK() OVER (PARTITION BY sm.tenant_id ORDER BY COUNT(b.id) DESC) AS rank_by_bookings
FROM staff_members sm
JOIN profiles p      ON p.id = sm.profile_id
LEFT JOIN bookings b ON b.staff_id = sm.id AND b.status = 'completed'
                     AND b.created_at >= now() - interval '30 days'
LEFT JOIN gratuities g ON g.staff_id = sm.id
                       AND g.created_at >= now() - interval '30 days'
LEFT JOIN reviews r  ON r.staff_id = sm.id
                     AND r.created_at >= now() - interval '30 days'
GROUP BY sm.id, sm.tenant_id, sm.profile_id, p.full_name
WITH DATA;

CREATE UNIQUE INDEX idx_staff_leaderboard_id ON staff_leaderboard(staff_id);
CREATE INDEX idx_staff_leaderboard_tenant   ON staff_leaderboard(tenant_id, rank_by_bookings);

-- Refresh daily at 23:00 UTC (00:00 WAT)
SELECT cron.schedule(
  'refresh-staff-leaderboard',
  '0 23 * * *',
  $$REFRESH MATERIALIZED VIEW CONCURRENTLY staff_leaderboard;$$
);
```

### Paystack Webhook (confirm-payment Edge Function)

- HMAC-SHA-512 signature verification on every request
- `charge.success` → `held → confirmed`, loyalty credit (idempotent INSERT), schedule reminder automation_jobs
- `charge.failed` → cancel booking, trigger waitlist notification
- Payout to providers via Paystack Transfer API (split: platform commission withheld, remainder to provider recipient code)

### Franchise Royalty Split

```sql
-- Computed at booking completion
-- Provider receives: total - platform_commission - franchise_royalty
-- config values from tenants.config for the branch's franchise tenant
SELECT
  b.total_amount_kobo,
  ROUND(b.total_amount_kobo * (t_platform.config->>'platform_commission_pct')::numeric / 100) AS platform_fee_kobo,
  ROUND(b.total_amount_kobo * (t_franchise.config->>'franchise_royalty_pct')::numeric / 100)  AS royalty_kobo
FROM bookings b
JOIN tenants t_branch    ON t_branch.id = b.tenant_id
JOIN tenants t_franchise ON t_franchise.id = t_branch.parent_id
JOIN tenants t_platform  ON t_platform.tenant_level = 'platform'
WHERE b.id = $1;
```

## Section 12 — Multi-Tenant Architecture

### Tenant Config Inheritance

Config values cascade from Platform → Country → Enterprise → Franchise → Branch. A branch-level override takes precedence. The `tenants.config` jsonb is the single source of truth.

```sql
-- Resolve effective config for a branch (walk up the tree)
CREATE OR REPLACE FUNCTION get_effective_config(p_tenant_id uuid, p_key text)
RETURNS jsonb LANGUAGE sql STABLE SECURITY DEFINER AS $$
  WITH RECURSIVE tenant_chain AS (
    SELECT id, parent_id, config, 1 AS depth FROM tenants WHERE id = p_tenant_id
    UNION ALL
    SELECT t.id, t.parent_id, t.config, tc.depth + 1
    FROM tenants t JOIN tenant_chain tc ON t.id = tc.parent_id
  )
  SELECT config -> p_key
  FROM tenant_chain
  WHERE config ? p_key
  ORDER BY depth ASC
  LIMIT 1;
$$;
```

## Section 13 — WRF Certification

All Edge Functions deployed on UrbanServe satisfy the 8 WRF requirements:

| Requirement | Implementation |
|-------------|---------------|
| 1. Authenticate | JWT verified via `supabase.auth.getUser()` on every request |
| 2. Resolve Tenant | `tenant_id` from request body, validated against staff membership |
| 3. Validate RBAC | Role checked from `staff_members.role` before any write |
| 4. Execute Idempotently | `idempotency_key` UUID; INSERT with UNIQUE constraint; 409 on replay |
| 5. Persist State Consistently | All state changes via Supabase transactions or `SECURITY DEFINER` RPCs |
| 6. Emit Audit Records | `audit_logs` INSERT on every status change, payment event, coupon use |
| 7. Publish Telemetry | `platform_metrics` INSERT with workstream + metric_name + dimensions |
| 8. Recover Gracefully | pg_cron releases stale holds; automation_jobs retry with exponential backoff |
