## Section 1 — Product Requirements Document

### 1.1 Vision

Kenya's beauty industry is a KES 40B+ annual market served almost entirely by walk-ins and informal WhatsApp chains. GlamPlus digitises the full service commerce lifecycle for hair salons, nail studios, and beauty spas — giving customers a seamless booking experience (staff selection, M-Pesa deposit, SMS reminder) and giving salon owners their first real operations layer (staff schedules, no-show policy enforcement, loyalty programs, and cross-branch analytics). In three years, GlamPlus is Kenya's default beauty booking platform, operating in 5 cities, hosting 2,000 salon branches, and processing KES 500M in annual appointment deposits.

### 2.3 Data Flow Narratives

#### Flow 1: Customer Registration (Phone OTP via Africa's Talking)
1. Customer enters phone number (+254…) in app
2. App calls `POST /auth/send-otp` (Edge Function)
3. Edge Function: rate-check (max 3 OTPs per phone per 10 min), generate 6-digit OTP, bcrypt hash, insert `phone_otps` row, call Africa's Talking SMS API
4. Africa's Talking delivers SMS to customer's phone
5. Customer enters OTP in app
6. App calls `POST /auth/verify-otp`
7. Edge Function: find unexpired row, compare bcrypt hash, mark verified, call `supabase.auth.admin.createUser` or sign in
8. Supabase returns JWT — app stores in SecureStore (mobile) or httpOnly cookie (web)
9. Edge Function creates `users` + `customer_profiles` row; triggers onboarding flow

#### Flow 2: SORF Booking Lifecycle (Full 18-Stage)
1. Customer searches for "hair braiding" near her location → map view shows 8 nearby salons
2. Selects GlamPlus Westlands → views Fatuma's profile (stylists, services, reviews)
3. Picks "Box Braids Full Head" (KES 3,500), selects Fatuma, chooses Thursday 10am
4. App calls `POST /bookings/hold` → booking created (status: `held`, `held_until` = now + 15 min)
5. App presents M-Pesa STK Push: "Pay KES 1,050 deposit (30%) to confirm your slot"
6. Customer confirms on M-Pesa handset → `POST /mpesa/stk-push` → Daraja C2B initiated
7. M-Pesa delivers STK Push; customer enters PIN
8. Daraja callback hits `POST /webhooks/daraja` → HMAC verified, booking transitions `held` → `confirmed`
9. Automation fires `booking.confirmed`: SMS confirmation to customer and Fatuma via Africa's Talking
10. 24h before: pg_cron automation sends reminder SMS in Swahili: "Kumbuka miadi yako kesho saa 4 asubuhi na Fatuma, GlamPlus Westlands."
11. Customer arrives → Amina (front desk) taps "Check In" → `PATCH /bookings/:id/checkin` → status: `checked_in`
12. Fatuma starts service → taps "Start" → status: `in_progress`; SLA clock begins
13. Service complete → Fatuma taps "Done" → status: `completed`
14. Automation fires `booking.completed`: remaining balance (KES 2,450) requested via second M-Pesa STK Push; rating SMS sent within 30 min
15. Wanjiru rates 5 stars → loyalty credit: 3,500 points added to her `loyalty_accounts` row
16. 28 days later: AI re-booking nudge — push + SMS: "Time for your next braiding session! Fatuma has openings next week."
17. Stage 17 (if no-show): if `checked_in` not received within 30 min of start → automation marks `no_show`, deposits forfeited per policy, no_show counter incremented
18. Stage 18: cancellation trigger → waitlist entry for same slot + Fatuma is promoted and notified via SMS

#### Flow 3: Deposit Payment via M-Pesa Daraja C2B STK Push
1. `POST /bookings/hold` creates booking row with status `held`, `held_until` = now + 15 min
2. `POST /payments/initiate` called with booking_id, amount = deposit_amount, phone
3. Edge Function: create `momo_transactions` row (status: `pending`, provider: `mpesa_ke`, idempotency_key = `booking-{id}-deposit`)
4. Call Daraja `oauth/v1/generate` → get access token (cached 55 min in Deno KV)
5. Call Daraja `mpesa/stkpush/v1/processrequest` with BusinessShortCode, Timestamp, Password (base64 shortcode+passkey+timestamp), Amount, PhoneNumber, AccountReference, TransactionDesc
6. Daraja returns CheckoutRequestID — stored in `momo_transactions.provider_reference`
7. Customer receives STK Push on phone, enters M-Pesa PIN
8. Daraja sends callback to `POST /webhooks/daraja/c2b`
9. Edge Function: verify HMAC SHA-256 signature against `DARAJA_WEBHOOK_SECRET`, check idempotency (skip if already processed)
10. On success: update `momo_transactions` (status: `success`), update booking (status: `confirmed`), clear `held_until`
11. On failure: update `momo_transactions` (status: `failed`), release hold (booking: `cancelled`), notify customer

#### Flow 4: Waitlist Notification on Cancellation
1. Customer cancels booking → `PATCH /bookings/:id/cancel` → status: `cancelled`
2. `on_booking_cancelled_notify_waitlist` trigger fires (see sql-patterns.md)
3. Trigger finds first `waitlist_entries` row for same service, branch, and overlapping slot window; notifies via `pg_notify('waitlist_slot_available', payload)`
4. Edge Function `realtime-worker` receives notification, sends SMS via Africa's Talking: "A slot opened for Box Braids with Fatuma at GlamPlus Westlands on Thursday 10am. Reply YES to book."
5. Customer replies → `POST /waitlist/accept` → new hold created (15 min); waitlist entry marked `notified`
6. If no response in 15 min: next waitlist entry is promoted

### Helper Functions

```sql
-- Auto-update updated_at on every row modification
CREATE OR REPLACE FUNCTION update_updated_at()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at = now();
  RETURN NEW;
END;
$$;

-- Returns tenant_id for the currently authenticated user (used in RLS policies)
CREATE OR REPLACE FUNCTION current_user_tenant_id()
RETURNS uuid LANGUAGE sql STABLE SECURITY DEFINER AS $$
  SELECT tenant_id FROM users WHERE id = auth.uid();
$$;

-- Returns true if the calling user has the super_admin role
CREATE OR REPLACE FUNCTION is_super_admin()
RETURNS boolean LANGUAGE sql STABLE SECURITY DEFINER AS $$
  SELECT EXISTS (
    SELECT 1 FROM users WHERE id = auth.uid() AND role = 'super_admin'
  );
$$;

-- Generates a 6-digit numeric OTP
CREATE OR REPLACE FUNCTION generate_otp()
RETURNS text LANGUAGE sql AS $$
  SELECT lpad(floor(random() * 1000000)::text, 6, '0');
$$;
```

-- Trigger: when a booking is cancelled or marked no_show, notify the next waitlist entry
CREATE OR REPLACE FUNCTION notify_waitlist_on_cancellation()
RETURNS TRIGGER LANGUAGE plpgsql AS $$
DECLARE
  v_entry waitlist_entries%ROWTYPE;
BEGIN
  IF NEW.status IN ('cancelled', 'no_show') AND OLD.status NOT IN ('cancelled', 'no_show') THEN
    SELECT * INTO v_entry
    FROM waitlist_entries
    WHERE branch_id  = NEW.branch_id
      AND service_id = NEW.service_id
      AND (staff_id  = NEW.staff_id OR staff_id IS NULL)
      AND window_start <= NEW.starts_at
      AND window_end   >= NEW.ends_at
      AND status       = 'waiting'
      AND expires_at   > now()
    ORDER BY created_at ASC
    LIMIT 1;

    IF FOUND THEN
      UPDATE waitlist_entries
        SET status = 'notified', notified_at = now()
      WHERE id = v_entry.id;

      -- pg_notify fires Edge Function worker to send SMS
      PERFORM pg_notify(
        'waitlist_slot_available',
        json_build_object(
          'waitlist_id',  v_entry.id,
          'customer_id',  v_entry.customer_id,
          'booking_id',   NEW.id,
          'branch_id',    NEW.branch_id,
          'staff_id',     NEW.staff_id,
          'starts_at',    NEW.starts_at
        )::text
      );
    END IF;
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER on_booking_cancelled_notify_waitlist
  AFTER UPDATE ON bookings
  FOR EACH ROW EXECUTE FUNCTION notify_waitlist_on_cancellation();

### Materialised View — Branch KPIs

```sql
-- Refreshed every 15 min by pg_cron
CREATE MATERIALIZED VIEW branch_kpis AS
SELECT
  b.id                                                         AS branch_id,
  b.business_id,
  b.tenant_id,
  b.name                                                       AS branch_name,
  count(bk.id) FILTER (WHERE bk.created_at >= now() - interval '30 days')  AS bookings_30d,
  count(bk.id) FILTER (WHERE bk.status = 'completed' AND bk.created_at >= now() - interval '30 days') AS completions_30d,
  count(bk.id) FILTER (WHERE bk.status = 'no_show'   AND bk.created_at >= now() - interval '30 days') AS no_shows_30d,
  coalesce(sum(bk.price_kes) FILTER (WHERE bk.status = 'completed' AND bk.created_at >= now() - interval '30 days'), 0) AS revenue_30d_kes,
  round(avg(r.rating) FILTER (WHERE r.created_at >= now() - interval '30 days'), 2) AS avg_rating_30d,
  count(DISTINCT bk.staff_id) FILTER (WHERE bk.status = 'completed' AND bk.starts_at >= date_trunc('day', now())) AS active_staff_today
FROM branches b
LEFT JOIN bookings bk ON bk.branch_id = b.id
LEFT JOIN reviews  r  ON r.branch_id  = b.id
WHERE b.is_active = true
GROUP BY b.id, b.business_id, b.tenant_id, b.name;

CREATE UNIQUE INDEX ON branch_kpis (branch_id);

-- pg_cron job to refresh every 15 minutes
SELECT cron.schedule(
  'refresh-branch-kpis',
  '*/15 * * * *',
  $$REFRESH MATERIALIZED VIEW CONCURRENTLY branch_kpis$$
);
```

## Section 7 — Automation Engine

### Event Catalogue (SORF-Aligned)

| Event | Trigger | Actions |
|---|---|---|
| `booking.held` | Booking created with status `held` | Start 15-min hold countdown; log audit |
| `booking.confirmed` | Deposit paid; status → `confirmed` | SMS to customer + stylist; push notification to customer; update waitlist availability |
| `booking.checked_in` | Staff marks `checked_in` | Notify stylist; log check-in time; update KPI |
| `booking.started` | Staff marks `in_progress` | Start SLA timer; notify customer ("Your service has started") |
| `booking.completed` | Staff marks `completed` | Initiate balance STK Push; credit loyalty points; trigger rating SMS (30 min delay); release wallet hold |
| `booking.cancelled` | Status → `cancelled` | Evaluate refund eligibility per policy; initiate B2C refund if eligible; notify waitlist (trigger fires); send cancellation SMS |
| `booking.no_show` | pg_cron marks `no_show` | Increment no_show_count on customer; evaluate no-show policy; if max_no_shows reached: set flag for prepayment requirement; notify branch manager |
| `booking.disputed` | Dispute raised by customer or staff | Freeze payout; notify branch manager; create dispute record; log audit |
| `payment.confirmed` | Daraja C2B callback success | Update booking status to `confirmed`; clear `held_until`; update `momo_transactions` |
| `payment.failed` | Daraja C2B callback failure | Release hold → status `cancelled`; notify customer with retry link |
| `waitlist.notified` | Trigger fires on cancellation | Send SMS to next waitlist customer via Africa's Talking; set 15-min acceptance window |
| `loyalty.credited` | Booking `completed` | Insert `loyalty_transactions` row; check tier upgrade threshold; send tier upgrade SMS if upgraded |
| `reminder.24h` | pg_cron 24h before `starts_at` | Send SMS + push: appointment tomorrow with stylist name and branch address |
| `reminder.2h` | pg_cron 2h before `starts_at` | Send SMS: "Your appointment is in 2 hours" with directions link |
| `ai.noshow_risk` | Daily at 22:00 EAT | Score tomorrow's bookings; flag high-risk (>60%); create automation_jobs for branch manager SMS nudge |
| `ai.rebook_nudge` | 28 days post-completion | Send push + SMS nudge for hair clients; 14 days for nail clients; personalised with last stylist name |

| Job Name | Schedule | Action |
|---|---|---|
| `release-expired-holds` | `*/5 * * * *` | Cancel bookings in `held` state past `held_until` |

```typescript
// Daraja C2B callback HMAC verification (SHA-256)
import { createHmac } from "node:crypto";

function verifyDarajaSignature(rawBody: string, signature: string, secret: string): boolean {
  const expected = createHmac("sha256", secret)
    .update(rawBody)
    .digest("hex");
  return expected === signature;  // timing-safe comparison recommended in production
}
```

### Paystack / Daraja Split Configuration
M-Pesa does not natively support split payouts at checkout. Platform fee is collected via a two-step flow:
1. Full payment goes to platform Paybill

3. Daily reconciliation job verifies sum of payouts equals sum of deposits minus platform fees

- **Roles**: customer, staff (stylists), branch_manager, franchise_owner, super_admin inferred from the prompt
- **SORF lifecycle**: All 18 stages implemented; 9-state booking_status enum is the source of truth for appointment state
- **Multi-tenancy**: Full RLS multi-tenancy applied — each salon group is a separate tenant; a single GlamPlus deployment can host multiple competing salon brands
- **Geolocation**: PostGIS included for branch proximity search; staff location tracking not included (stationary staff, not dispatch model)
