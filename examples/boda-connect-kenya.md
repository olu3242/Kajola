## Section 1 — Product Requirements Document

### 1.1 Vision

Kenya's boda-boda sector moves over 20 million passengers per day, yet 90% of riders operate as solo independents with no earnings visibility, no job queue, and no accident or income protection. Saccos (rider cooperatives) manage fleets on WhatsApp and paper notebooks. BodaConnect transforms this: riders join a Sacco tenant on the platform, receive job assignments via app, settle fares through M-Pesa, and build a verifiable earnings history that unlocks micro-loans and insurance products. Saccos get a real-time dispatch dashboard, daily revenue reports, and direct STK-Push settlement. In three years, BodaConnect is the operating system for Kenya's boda-boda economy — 50,000 active riders, KES 2B+ in monthly GMV, and the data backbone that finally makes boda-boda bankable.

### 1.2 Target Personas

#### Persona 1: Kamau — The Boda-Boda Rider
- **Age range**: 22–40
- **Tech comfort**: Low–Medium (feature phone or entry-level Android)
- **Primary device**: Tecno Spark or Samsung A-series; USSD fallback for feature phones
- **Language**: Swahili primary, English secondary
- **Jobs to be done**:
  - Receive job assignments and navigate to pickup without burning data
  - Collect fares via M-Pesa so no cash changes hands
  - See daily/weekly earnings and compare to Sacco peers
  - Build a verifiable trip history for loan and insurance applications
- **Current frustrations**:
  - No-show passengers; cash disputes with no record
  - Sacco chairperson collecting daily levy in cash with no receipt
  - Cannot prove income to banks — excluded from formal credit

#### Persona 2: Wanjiru — The Sacco Operations Manager
- **Age range**: 30–50
- **Tech comfort**: Medium (smartphone + occasional laptop)
- **Primary device**: Android smartphone; web dashboard for reporting
- **Jobs to be done**:
  - Dispatch riders to queued jobs and track completion in real time
  - Collect daily levies automatically via M-Pesa — eliminate cash
  - Run payroll reconciliation: total fares earned vs. levies deducted
  - Suspend non-compliant riders or those with low ratings
- **Current frustrations**:
  - WhatsApp group dispatch — no accountability, riders ignore messages
  - Daily levy collection takes 3 hours of manual reconciliation
  - No single view of fleet location or idle capacity

#### Persona 3: Akinyi — The Passenger
- **Age range**: 18–45
- **Tech comfort**: Medium–High
- **Primary device**: Android (Samsung Galaxy A-series or Infinix)
- **Jobs to be done**:
  - Book a confirmed boda from her neighbourhood at a fixed fare
  - Pay by M-Pesa Lipa na M-Pesa — no cash, no fare negotiation
  - Rate the ride so bad actors are flagged to the Sacco
  - Share live trip tracking with family for safety
- **Current frustrations**:
  - Fare negotiation every trip — never knows the price upfront
  - No accountability when a rider is rude or unsafe
  - Unsafe at night — no one knows which rider she boarded

### 1.3 Core User Journeys

#### Journey 1: Rider Onboarding
1. Sacco Operations Manager invites rider via SMS link (Africa's Talking)
2. Rider opens link → enters phone number → receives OTP → verifies identity
3. Rider uploads national ID photo + PSV licence via app
4. Sacco manager approves KYC → rider status moves `pending` → `active`
5. Rider's M-Pesa number is registered as settlement account

#### Journey 2: Passenger Books a Ride
1. Passenger opens app → selects origin (GPS pin) and destination
2. System calculates fare (distance-based KES rate) and shows nearest available rider
3. Passenger taps "Book" → M-Pesa STK Push sent to passenger's phone
4. Passenger enters M-Pesa PIN → payment confirmed via Daraja callback
5. Rider receives job assignment push notification + SMS fallback
6. Trip starts → live location shared with passenger and Sacco dashboard
7. Trip ends → fare minus Sacco levy auto-settled to rider's M-Pesa

#### Journey 3: Sacco Daily Levy Collection
1. Midnight cron job calculates each rider's earnings for the day
2. System deducts configured levy percentage (e.g. 10%) and initiates M-Pesa B2C payout to rider for net amount
3. Sacco's M-Pesa Till account receives gross; Sacco accounting dashboard shows breakdown
4. Riders with zero trips get a 09:00 push notification to check availability

#### Journey 4: Dispute Resolution
1. Passenger reports issue within 24 hours of trip completion
2. System freezes rider's next payout (idempotent escrow hold)
3. Sacco operations manager reviews trip recording (GPS track + fare receipt)
4. Manager resolves → release or partial refund via M-Pesa B2C reversal

### 1.4 Non-Functional Requirements
- **Availability**: 99.5% uptime (allow 3.6 hrs/month maintenance)
- **Offline**: Rider app caches active job details and last known map tile for 4 hours offline; queues GPS pings locally and syncs on reconnect
- **Latency**: STK Push initiation < 3s; job dispatch notification < 5s
- **Data efficiency**: Rider app < 2 MB initial download; map tiles loaded lazily
- **USSD fallback**: Riders on feature phones can check earnings via USSD (*384*BodaConnect#)
- **Language**: Swahili (sw-KE) and English (en-KE) — all copy and SMS templates bilingual
- **Regulatory**: Compliant with Kenya Data Protection Act 2019; CBK mobile money guidelines

```sql
CREATE POLICY riders_tenant ON riders
  USING (tenant_id = current_user_tenant_id());

-- Trips: rider sees own trips, passenger sees own trips, manager sees all in tenant
CREATE POLICY trips_rider ON trips
  USING (
    tenant_id = current_user_tenant_id()
    AND (
      rider_id = auth.uid()::uuid
      OR passenger_id = auth.uid()::uuid
      OR current_setting('app.role', true) = 'manager'
    )
  );

-- GPS pings: tenant-scoped
CREATE POLICY gps_tenant ON trip_gps_pings
  USING (tenant_id = current_user_tenant_id());

-- M-Pesa transactions: manager + service role only
CREATE POLICY mpesa_manager ON mpesa_transactions
  USING (
    tenant_id = current_user_tenant_id()
    AND current_setting('app.role', true) IN ('manager','service')
  );
```

## Section 5 — Auth & Roles

### 5.1 Authentication Flow
1. User enters phone number (E.164 format: `254XXXXXXXXX`)
2. Africa's Talking SMS delivers 6-digit OTP (`phone_otps` table)
3. User submits OTP → verified server-side → Supabase `auth.users` session created
4. `app_metadata.tenant_id` and `app_metadata.role` set on signup completion

### 5.2 Role Matrix

| Role | Description | Assigned |
|------|-------------|---------|
| `rider` | Can receive jobs, submit GPS pings, view own earnings | On KYC approval |
| `passenger` | Can book trips, initiate STK Push, submit ratings | On phone verification |
| `manager` | Full Sacco dashboard: dispatch, KYC, reports, suspend riders | Sacco admin grants |
| `service` | Internal Edge Functions (service role key) | Never exposed to client |

### 5.3 OTP Table

```sql

  phone       text NOT NULL,
  otp_hash    text NOT NULL,   -- bcrypt hash — never store plain OTP
```

### 5.4 Security Rules
- OTP max attempts: 5; lock phone for 15 minutes on exceed
- OTPs expire in 10 minutes (shorter than default for mobile money safety)
- Rider app requests use rider JWT; never service role key on client
- M-Pesa callbacks authenticated by Daraja shared secret HMAC (see Section 8)

## Section 8 — Webhook & Security Patterns

### 8.1 Daraja Callback HMAC Verification

```typescript
// Daraja sends SHA-256 HMAC of the raw body
async function verifyDaraja(req: Request, secret: string): Promise<boolean> {
  const sig = req.headers.get("x-daraja-signature") ?? "";
  const body = await req.text();
  const key = await crypto.subtle.importKey(
    "raw", new TextEncoder().encode(secret),
    { name: "HMAC", hash: "SHA-256" }, false, ["sign"]
  );
  const mac = await crypto.subtle.sign("HMAC", key, new TextEncoder().encode(body));
  const hex = Array.from(new Uint8Array(mac))
    .map(b => b.toString(16).padStart(2, "0")).join("");
  return hex === sig;
}
```

### 8.2 M-Pesa STK Push Idempotency

```typescript
// trip_id is the natural idempotency key for STK Push
async function ensureIdempotent(tripId: string): Promise<boolean> {
  const { error } = await supabase
    .from("mpesa_transactions")
    .insert({
      idempotency_key: `stk_${tripId}`,
      direction: "c2b",
      status: "pending",
      tenant_id: tenantId,
      phone: passengerPhone,
      amount_kes: fareKes,
    });
  return !error; // false = duplicate request, skip STK Push
}
```

### 8.3 B2C Payout Security
- B2C security credential is RSA-encrypted with Safaricom's production public key
- Initiator password never stored in plain text
- All B2C calls logged to `mpesa_transactions` with `direction = 'b2c'`
- Payout only triggers after `trips.payment_status = 'paid'` (C2B confirmed)

### 8.4 KYC Document Storage
- Documents uploaded to Supabase Storage bucket `kyc-documents` (private, no public URL)
- Storage paths stored in `kyc_documents.storage_path`
- Signed URLs generated server-side with 60-second expiry for manager review
- Documents deleted from storage on rider offboarding (GDPR / Kenya DPA 2019)

## Section 9 — Offline & Resilience Strategy

### 9.1 Rider App Offline Mode
- Active job details cached in local SQLite (expo-sqlite) on assignment
- Map tiles for last known area cached up to 4 hours (react-native-maps offline layer)
- GPS pings queued in SQLite when offline; flushed on reconnect in FIFO order
- SMS fallback: Africa's Talking sends job assignment via SMS if push notification not acknowledged in 30 seconds

### 9.2 M-Pesa Network Resilience
- STK Push timeout: Daraja waits up to 60 seconds for PIN entry
- If callback not received in 90 seconds: poll Daraja QueryTransaction API (max 3 times, 30s apart)
- Idempotency key prevents double-charges on retry
- `mpesa_transactions.status` transitions: `pending` → `completed` | `failed` → `reversed`

### 9.3 Feature Phone / USSD Fallback
- Riders on feature phones access earnings via USSD `*384*BodaConnect#`
- USSD session handled by Africa's Talking USSD gateway → `ussd-handler` Edge Function
- Swahili menu tree:
  ```
  1. Mapato ya leo      (Today's earnings)
  2. Mapato ya wiki     (This week's earnings)
  3. Hali ya akaunti   (Account status)
  4. Wasiliana nasi    (Contact support)
  ```
- USSD sessions expire in 180 seconds (Africa's Talking default)

### 9.4 Circuit Breaker for External APIs
- Africa's Talking SMS: if 3 consecutive failures → fall back to Supabase Realtime push notification
- Daraja STK Push: if timeout → present manual payment instruction with Sacco Paybill number
- PostGIS nearest-rider query capped at 200ms; fallback to last known location if index scan exceeds limit

## Assumptions Made

1. **M-Pesa Daraja API access**: BodaConnect will obtain a Safaricom Daraja C2B + B2C production API credential. Sandbox credentials available immediately for development.
2. **Africa's Talking credentials**: SMS and USSD integration assumes an AT account with `BodaConnect` sender ID registered and Kenya shortcode allocated.
3. **Sacco as tenant**: Each Sacco is an independent tenant with its own M-Pesa Till/Paybill, levy percentage, and rider roster. Cross-Sacco trips are out of scope for MVP.
4. **KES whole shillings**: All amounts stored as integers (KES). No sub-shilling transactions. M-Pesa enforces whole-shilling amounts natively.
5. **PSV licence validation**: Phase 1 stores licence number as text; Phase 2 integrates NTSA API for real-time verification.
6. **USSD shortcode**: Platform uses a shared AT shortcode in development; dedicated shortcode (`*384*XXXX#`) registered with CA Kenya for production.
7. **PostGIS extension**: Supabase project has PostGIS enabled (`CREATE EXTENSION IF NOT EXISTS postgis`).
8. **Kenya Data Protection Act compliance**: Personal data (phone, ID, location) is stored within Supabase's Africa (cape-town) region or EU region pending CA confirmation; KYC documents deleted within 30 days of offboarding.
9. **Bilingual copy**: All user-facing strings managed via i18n JSON files (`sw-KE.json`, `en-KE.json`); RTL not required for Swahili.
10. **Rating MVP**: Post-trip ratings are optional for passengers; mandatory for riders above 100 trips. Dispute resolution is manual (Sacco manager) in Phase 1.
