## Section 1 — Product Requirements Document (PRD)

### 1.1 Vision

CleanRun is Nigeria's first tech-enabled laundry-as-a-service platform. Customers schedule pickups from their home or office; CleanRun riders collect the garments, deliver them to a vetted partner laundromat for processing, then return the clean clothes on the agreed delivery date. The platform removes every friction point — no need to locate a laundry, negotiate prices, or wonder if clothes are damaged. By 2029, CleanRun is the default laundry OS for Lagos, Abuja, and Port Harcourt: trusted by 200,000 households, powering 50 laundromat partners, and generating ₦1.5B in annual GMV.

|---|---|---|---|
| Authentication | Supabase Auth | Phone OTP login; JWT with `tenant_id` + `role` claims | Termii SMS OTP |

| SMS / OTP | Termii | OTP delivery, booking confirmations, rider ETA alerts | API key |
| Maps | Mapbox | Rider location map in admin dispatch board and customer app | Public token |
| WhatsApp (P1) | Africa's Talking | Booking via WhatsApp; status update messages | API key + username |

### 2.3 Data Flow Narratives

**1. Phone OTP registration**
Customer enters phone → Supabase Auth calls Termii `send-otp` → 6-digit code SMS → Customer submits code → Supabase verifies → JWT issued with `tenant_id` + `role: customer` claims → `customers` row upserted.

**2. Booking creation (pickup scheduling)**
Customer selects tier + slot → `POST /book-pickup` Edge Function → availability check against `availability_windows` → `INSERT INTO bookings (status='held', held_until=now()+15min)` → `EXCLUDE USING gist` fires (409 if rider busy) → Paystack transaction initialized for deposit amount → payment URL returned to customer.

**3. Payment capture (Paystack webhook)**
Customer pays deposit → Paystack `charge.success` event → `POST /confirm-payment` → HMAC-SHA-512 signature verified → `UPDATE bookings SET status='confirmed'` → loyalty points credited (idempotent) → `automation_jobs` rows inserted for SMS reminders → 200 OK.

**4. GPS ping and Realtime broadcast**
Rider app sends `POST /gps-ping` every 10 seconds → Edge Function inserts row in `gps_pings` (append-only guard triggers) → Supabase Realtime broadcasts on channel `gps:booking:{id}` → Customer app updates rider marker on map.

```sql
-- Guard: reject pings with future timestamps beyond 30 seconds
CREATE OR REPLACE FUNCTION guard_gps_ping_timestamp()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.recorded_at > now() + interval '30 seconds' THEN
    RAISE EXCEPTION
      'gps_ping.recorded_at cannot be more than 30 seconds in the future (got %)',
      NEW.recorded_at;
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_guard_gps_ping_timestamp
  BEFORE INSERT ON gps_pings
  FOR EACH ROW EXECUTE FUNCTION guard_gps_ping_timestamp();

-- Deny UPDATE and DELETE — gps_pings is append-only
CREATE OR REPLACE FUNCTION deny_gps_ping_mutation()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  RAISE EXCEPTION 'gps_pings is append-only: % operation is not permitted', TG_OP;
END;
$$;

CREATE TRIGGER trg_deny_gps_ping_update
  BEFORE UPDATE ON gps_pings
  FOR EACH ROW EXECUTE FUNCTION deny_gps_ping_mutation();

CREATE TRIGGER trg_deny_gps_ping_delete
  BEFORE DELETE ON gps_pings
  FOR EACH ROW EXECUTE FUNCTION deny_gps_ping_mutation();

-- Notify waitlist when booking is cancelled or no-show
CREATE OR REPLACE FUNCTION notify_waitlist()
RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_entry waitlist_entries%ROWTYPE;
BEGIN
  IF NEW.status IN ('cancelled', 'no_show')
     AND OLD.status NOT IN ('cancelled', 'no_show') THEN

    SELECT * INTO v_entry
    FROM waitlist_entries
    WHERE branch_id   = NEW.branch_id
      AND tenant_id   = NEW.tenant_id
      AND slot_date   = NEW.starts_at::date
      AND notified_at IS NULL
    ORDER BY created_at ASC
    LIMIT 1;

    IF FOUND THEN
      INSERT INTO automation_jobs (
        tenant_id, booking_id, job_type, payload, scheduled_for, idempotency_key
      ) VALUES (
        NEW.tenant_id,
        NEW.id,
        'notify_waitlist_customer',
        jsonb_build_object(
          'waitlist_entry_id', v_entry.id,
          'customer_id',       v_entry.customer_id,
          'branch_id',         NEW.branch_id,
          'slot_date',         NEW.starts_at::date
        ),
        now(),
        'waitlist_' || v_entry.id || '_' || NEW.id
      )
      ON CONFLICT (idempotency_key) DO NOTHING;

      UPDATE waitlist_entries SET notified_at = now() WHERE id = v_entry.id;
    END IF;
  END IF;
  RETURN NEW;
END;
$$;

-- Track no-show count on customer profile
CREATE OR REPLACE FUNCTION track_customer_no_show()
RETURNS trigger LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_policy jsonb;
BEGIN
  IF NEW.status = 'no_show' AND OLD.status != 'no_show' THEN
    UPDATE customers
    SET no_show_count = no_show_count + 1
    WHERE id = NEW.customer_id;

    SELECT no_show_policy INTO v_policy
    FROM branches WHERE id = NEW.branch_id;

    IF (SELECT no_show_count FROM customers WHERE id = NEW.customer_id)
       >= (v_policy->>'max_strikes')::int THEN
      UPDATE customers SET require_prepayment = true WHERE id = NEW.customer_id;
    END IF;
  END IF;
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_track_customer_no_show
  AFTER UPDATE ON bookings
  FOR EACH ROW EXECUTE FUNCTION track_customer_no_show();

-- Materialised view — branch KPIs (refreshed every 15 min by pg_cron)

CREATE MATERIALIZED VIEW branch_kpis AS
SELECT
  b.branch_id,
  b.tenant_id,
  date_trunc('day', b.starts_at)                                      AS kpi_date,
  COUNT(*) FILTER (WHERE b.status = 'completed')                      AS completed_orders,
  COUNT(*) FILTER (WHERE b.status = 'no_show')                        AS no_show_count,
  COUNT(*) FILTER (WHERE b.status = 'cancelled')                      AS cancellation_count,
  COALESCE(SUM(b.total_ngn)    FILTER (WHERE b.status = 'completed'), 0) AS revenue_ngn,
  COALESCE(SUM(b.weight_kg_actual) FILTER (WHERE b.status = 'completed'), 0) AS weight_processed_kg,
  ROUND(AVG(b.weight_kg_actual) FILTER (WHERE b.status = 'completed'), 2) AS avg_order_kg,
  now()                                                                AS refreshed_at
FROM bookings b
GROUP BY b.branch_id, b.tenant_id, date_trunc('day', b.starts_at)
WITH DATA;

CREATE UNIQUE INDEX ON branch_kpis (branch_id, kpi_date);
```

### POST /functions/v1/confirm-payment
**Auth**: `x-paystack-signature` HMAC-SHA-512 header
**Purpose**: Transition booking `held → confirmed` on successful Paystack payment

**Request** (Paystack `charge.success` payload):
```json

  "data": {
    "reference": "cleanrun_booking_uuid_1722834600",

    "currency": "NGN",
    "metadata": {
      "booking_id": "uuid",
      "tenant_id": "uuid",
      "customer_id": "uuid"
    }
  }
}
```

**Transition logic (Edge Function)**:
1. Verify `x-paystack-signature`: `HMAC-SHA-512(rawBody, PAYSTACK_SECRET_KEY)` — reject with 401 on mismatch
2. Resolve booking; assert `status = 'held'` and `held_until > now()`
3. `UPDATE bookings SET status = 'confirmed', payment_status = 'paid'`
4. Credit loyalty: 1 point per ₦100; `INSERT INTO loyalty_transactions ... ON CONFLICT (idempotency_key) DO NOTHING`
5. Schedule automation jobs: `pickup_reminder_24h` and `pickup_reminder_2h`
6. Return `200 OK`

### Edge Function: confirm-payment (HMAC verification)

```typescript
// Verify Paystack HMAC-SHA-512 signature
const rawBody = await req.text()
const signature = req.headers.get('x-paystack-signature') ?? ''
const expectedSig = createHmac('sha512', Deno.env.get('PAYSTACK_SECRET_KEY')!)
  .update(rawBody)
  .digest('hex')

if (signature !== expectedSig) {
  return new Response('Unauthorized', { status: 401 })
}

const event = JSON.parse(rawBody)
if (event.event !== 'charge.success') {
  return new Response('OK', { status: 200 }) // acknowledge non-payment events
}

const { booking_id, tenant_id, customer_id } = event.data.metadata

// Transition held → confirmed
await supabase
  .from('bookings')
  .update({ status: 'confirmed', payment_status: 'paid' })
  .eq('id', booking_id)
  .eq('status', 'held') // guard: only transition from held
  .eq('tenant_id', tenant_id)

// Credit loyalty points — idempotent
const amountNgn = event.data.amount / 100
const points = Math.floor(amountNgn / 100)
await supabase.from('loyalty_transactions').insert({
  tenant_id,
  account_id: loyaltyAccountId,
  booking_id,
  points_delta: points,
  reason: 'order_payment',
  idempotency_key: `loyalty_${booking_id}_${event.data.reference}`,
}).onConflict('idempotency_key').ignore()
```

## Section 10 — Scaling Plan

### 10,000 active customers

- Single Supabase project with connection pooling (pgBouncer built-in; pool size 10)
- `gps_pings` table: partition by `recorded_at` month using Postgres declarative partitioning — prevents bloat from continuous 10s pings
- Indexes on `bookings(branch_id, starts_at, status)` and `gps_pings(booking_id, recorded_at DESC)`
- Supabase Realtime: one channel per active booking (`gps:booking:{id}`); limit to 50 concurrent channels per client
- `latest_gps_pings` view: used by dispatch map; replace with `MATERIALIZED VIEW` refreshed every 30s at this scale

### 100,000 active customers

- Supabase read replicas for admin dispatch board queries
- `gps_pings` archive: move pings > 30 days to cold storage; keep hot partitions for active orders only
- Separate Supabase projects per city cluster (Lagos, Abuja, Port Harcourt) — reduces cross-region latency for RLS queries
- GPS ping batching in Expo app: client buffers 5 pings, sends batch every 50s instead of individual pings (reduces Edge Function invocations by 80%)
- Paystack Split Payments API: auto-settle laundromat partner 70% share at order completion (eliminate manual settlements)

### 1,000,000 active customers

- Sharding by tenant across Supabase orgs; tenant router service maps `tenant_id` to project URL
- `gps_pings` moved to TimescaleDB hypertable for time-series compression and continuous aggregate views
- ML ETA model: train on historical GPS velocity + route + time-of-day → ±3-minute ETA predictions
- WhatsApp Business API (direct) as primary booking channel — replaces SMS for customers on WhatsApp (>80% of Nigerian smartphone users)
- Drone/robot delivery pilot for ultra-dense urban zones (Victoria Island, Wuse II)

## Assumptions Made

- **Multi-tenancy**: Each laundromat partner group (operator) is a `tenant`; branches are individual processing locations; RLS enforces strict data isolation
- **Auth**: Phone OTP via Termii is the **only** auth method; email login is not supported at launch
- **Payment**: Paystack handles card, bank transfer, and USSD; cash-on-delivery is not supported at launch; balance is collected via a Paystack link sent after weigh-in
- **Weight pricing**: Customer provides estimated weight at booking for deposit calculation; rider weighs garments at pickup; final total recalculated; balance charged via separate Paystack link
- **GPS**: Rider app uses `expo-location` with `BackgroundFetch` background task; device must grant `LOCATION_BACKGROUND` permission; pings pause if booking status is `completed` or `cancelled`
- **Photos**: All job photos stored in private Supabase Storage bucket `job-photos`; served via 15-minute signed URLs; never public URLs
- **Slot conflict**: `EXCLUDE USING gist` on `(rider_id, branch_id, tstzrange)` prevents double-booking at DB level; rider_id may be NULL until admin assigns — the constraint only fires when `rider_id IS NOT NULL`
- **Laundromat partners**: Modelled as `branches` with processing `staff`; they receive order manifests via admin portal, not direct customer access
- **No-show policy**: After 2 missed pickups, customer `require_prepayment=true`; handled by `no_show_policy` jsonb on `branches` + `track_customer_no_show` trigger
- **Idempotency**: All payment and loyalty operations use `idempotency_key` UNIQUE constraint; Paystack webhook retries are safe
- **GPS append-only**: `gps_pings` has no UPDATE or DELETE triggers; `guard_gps_ping_timestamp` rejects pings with future timestamps > 30 seconds
- **Archive**: GPS pings older than 30 days are deleted daily by `pg_cron` to control table size; archived to S3 before deletion at scale
