### 2.3 Data Flow Narratives

#### Flow 1: User Registration (Phone OTP)
1. User enters phone number in app
2. App calls Edge Function `POST /auth/send-otp`
3. Edge Function: rate-check (max 3/10min), generate 6-digit OTP, bcrypt hash, insert `phone_otps` row, call Termii `send-otp` API
4. Termii delivers SMS to user's phone
5. User enters OTP in app
6. App calls Edge Function `POST /auth/verify-otp`
7. Edge Function: find unexpired row, compare bcrypt hash, mark verified, call `supabase.auth.admin.createUser` or sign in
8. Supabase returns JWT — app stores in SecureStore (mobile) or httpOnly cookie (web)
9. Edge Function creates `users` + `profiles` row for new users
10. App navigates to onboarding flow

#### Flow 2: SORF Booking Lifecycle (Service Commerce)
1. Customer browses provider profile → taps "Book Now" → selects service, staff member, and slot
2. App calls `POST /bookings/hold` — Edge Function creates booking row (status: `held`, `held_until` = now + 15 min)
3. If deposit required: App initiates payment flow (`POST /payments/initiate` → Paystack / M-Pesa STK Push)
4. On payment confirmation webhook: booking transitions `held` → `confirmed`; hold timer cancelled
5. pg_cron job runs every 5 min: releases all `held` bookings past `held_until` → status `cancelled`
6. 24h before: automation sends SMS reminder → customer replies "1" to confirm or "2" to cancel
7. Customer arrives: staff marks `checked_in` via dashboard `PATCH /bookings/:id/checkin`
8. Service starts: staff marks `in_progress` → clock starts for SLA tracking
9. Service ends: staff marks `completed` → automation queues payout to provider wallet
10. Rating prompt sent to customer (SMS or push) within 30 min of completion
11. No-show path: if booking not `checked_in` within 30 min of start time → automation marks `no_show`, applies no-show policy (block / require prepayment)
12. Waitlist trigger: on any `cancelled` or `no_show` event, trigger notifies next waitlist entry for the same slot

#### Flow 3: Payment Capture
1. Client initiates payment — app calls Edge Function `POST /payments/initiate`
2. Edge Function creates `transactions` row (status: `pending`), calls Paystack `initialize` API
3. Paystack returns authorization URL / reference
4. App opens Paystack checkout (WebView or redirect)
5. User completes payment on Paystack
6. Paystack sends webhook to Edge Function `POST /webhooks/paystack`
7. Edge Function: verify HMAC signature, check idempotency key, update `transactions` row (status: `success`)
8. Edge Function triggers automation event `payment.confirmed`
9. Automation job: credit provider wallet, update booking status, send SMS confirmation
10. Realtime broadcasts booking status change to both client and provider apps

#### Flow 4: Notification Dispatch
1. Automation event fires (e.g. `booking.confirmed`)
2. Notification job reads user preferences and contact info
3. For each channel (SMS, push, WhatsApp): check user opt-in, format message, call provider API
4. Log delivery result to `notification_logs` table
5. On failure: mark failed, retry up to 3 times with exponential backoff

{
  "phone": string,

{
  "access_token": string,
  "refresh_token": string,
  "user": { "id": uuid, "phone": string, "role": string }
}

- 400: Missing fields
- 401: Invalid or expired OTP

## Sections 6–11 — Abbreviated Templates

For sections 6–11, the template keys are:

**Section 6 — Monorepo**: Full directory tree with every package named and described. List all Edge Functions with their HTTP method, path, and purpose.

**Section 7 — Automation**: Complete event catalogue table (minimum 8 events) covering the full SORF lifecycle — include events for `booking.held`, `booking.confirmed`, `booking.checked_in`, `booking.completed`, `booking.no_show`, `booking.cancelled`, `payment.confirmed`, `waitlist.notified`, plus domain-specific events. Full `automation_jobs` schema. All cron jobs with exact pg_cron schedules (include: hold expiry every 5 min, reminder 24h before, no-show check 30 min post-start, waitlist cleanup, nightly reconciliation). HMAC verification pseudocode for each payment provider. AI Operations hooks: flag no-show probability > 60% before slot, suggest alternative staff when preferred staff has conflicts.

**Section 8 — Deployment**: Numbered steps (no vague instructions). Every env var in table format. GitHub Actions YAML outline (not pseudocode — actual job names and steps). Staging vs production config table.

**Section 9 — Monetization**: All rates as actual numbers (never "X%" or "TBD"). Use the following format for every revenue stream:

| Stream | Model | Rate | Implementation | Projected (1k/10k/100k monthly transactions) |
|---|---|---|---|---|
| [Stream name] | [transaction fee / subscription / listing fee / featured placement] | [exact ₦ amount or exact %] | [Paystack split / manual deduction / recurring plan / etc.] | [₦X / ₦Y / ₦Z per month] |

Rules:
- Every rate must be a specific number (e.g. `10%`, `₦5,000/month`, `₦500 flat fee`) — never `X%`, `TBD`, or a range without anchoring to a midpoint
- Revenue projections must use the exact rate, not a rounded estimate
- If platform uses Paystack split, specify the exact split percentage (e.g. `90% provider / 10% platform`)
- Include at minimum 2 revenue streams (e.g. transaction fee + SaaS subscription)
- Section 9.2 Pricing Tiers must include at least 2 tiers with exact per-month NGN / KES / GHS / XOF prices
- Section 9.3 or equivalent must compute monthly revenue at a realistic scale (e.g. 10k transactions × avg fee × rate = MRR estimate)

**Section 10 — Scaling**: Concrete actions at each threshold. Specific Supabase settings to change. Index strategies tied to query patterns. Cost estimates where relevant.

**Section 11 — Roadmap**: Weekly milestones for Q1. Feature-level milestones for Q2–Q4. Business impact for every milestone (not just technical deliverables).
